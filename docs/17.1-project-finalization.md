```json
  },

  "[javascript]": {

  },

  "files.trimTrailingWhitespace": true,

  "editor.tabSize": 2,
  "editor.detectIndentation": false,

  "files.eol": "\n"

```

---

# Explicação das configurações

## editor.formatOnSave

```json
"editor.formatOnSave": true
```

Sempre que um arquivo for salvo, o Visual Studio Code executará automaticamente o formatador configurado.

Isso elimina a necessidade de executar comandos de formatação manualmente durante o desenvolvimento.

---

## source.fixAll.eslint

```json
"source.fixAll.eslint": "always"
```

Executa automaticamente todas as correções possíveis identificadas pelo ESLint no momento em que o arquivo é salvo.

Sempre que existir uma correção automática disponível, ela será aplicada.

---

## source.organizeImports

```json
"source.organizeImports": "always"
```

Organiza automaticamente os imports do arquivo.

Exemplos:

- Remove imports não utilizados;
- Reorganiza a ordem dos imports;
- Mantém um padrão consistente entre todos os arquivos do projeto.

---

## editor.defaultFormatter

Define o Prettier como formatador oficial do projeto.

Isso garante que todos os arquivos utilizem exatamente o mesmo padrão de formatação.

---

## Configuração por linguagem

Os blocos:

- TypeScript
- TSX
- JavaScript
- JSX

garantem que o Prettier seja utilizado independentemente do tipo do arquivo.

---

## files.trimTrailingWhitespace

Remove automaticamente espaços em branco existentes ao final das linhas.

Essa prática mantém o repositório mais limpo e evita alterações desnecessárias no Git.

---

## files.insertFinalNewline

Garante que todos os arquivos terminem com uma linha em branco.

Essa convenção é adotada pela maioria das ferramentas utilizadas em projetos profissionais.

---

## editor.tabSize

Define o tamanho da indentação como dois espaços.

Todo o projeto utilizará a mesma configuração.

---

## editor.detectIndentation

Impede que o Visual Studio Code altere automaticamente a indentação de acordo com o arquivo aberto.

Dessa forma toda a equipe utilizará exatamente a mesma configuração.

---

## files.eol

Define que todas as quebras de linha serão gravadas utilizando o padrão LF.

Essa configuração evita diferenças entre Windows, Linux e macOS.

# Etapa 2 — Configuração da Infraestrutura de Testes

---

# Objetivo

Nesta etapa será configurada toda a infraestrutura necessária para execução de testes automatizados do projeto.

O objetivo não é criar testes relacionados às funcionalidades da aplicação, mas preparar toda a estrutura reutilizável que permitirá a criação de testes durante o desenvolvimento.

Além da configuração da infraestrutura, será criado um teste inicial de validação. Esse teste terá como única finalidade confirmar que todo o ambiente foi configurado corretamente.

Ao final desta etapa, o projeto possuirá uma infraestrutura de testes completamente configurada, validada e pronta para ser utilizada em qualquer projeto criado a partir deste Template.

---

# Por que configurar os testes nesta etapa?

Todo Template profissional deve fornecer uma infraestrutura pronta para testes.

Isso evita que cada novo projeto precise repetir toda a configuração de bibliotecas, arquivos, scripts e ambiente de execução.

Ao deixar essa infraestrutura preparada desde o início, o desenvolvimento das funcionalidades poderá ser acompanhado pela criação de testes sem qualquer configuração adicional.

Além disso, a criação de um teste inicial permite validar que toda a infraestrutura realmente está funcionando antes mesmo do desenvolvimento da aplicação.

---

Durante esta etapa serão realizados os seguintes procedimentos:

- Instalação das dependências necessárias;

- Organização da estrutura de testes;
- Criação dos scripts no `package.json`;

- Validação completa da configuração.

Nenhum teste relacionado às regras de negócio da aplicação será criado nesta etapa.

O foco permanece exclusivamente na preparação e validação da infraestrutura de testes.

# Explicação das dependências

## Vitest

Responsável pela execução dos testes automatizados.

Foi desenvolvido para funcionar em conjunto com o Vite, oferecendo inicialização rápida e excelente integração com projetos React.

Será o executor oficial dos testes deste Template.

---

## @vitest/ui

Disponibiliza uma interface gráfica para execução e acompanhamento dos testes.

Essa interface facilita a visualização dos testes executados, seus resultados e possíveis falhas durante o desenvolvimento.

Ela será utilizada pelo script:

```bash
pnpm test:ui
```

---

## @vitest/coverage-v8

Responsável pela geração dos relatórios de cobertura de testes.

Essa biblioteca informa quais partes do código estão cobertas pelos testes automatizados, permitindo identificar regiões ainda não testadas.

---

## @testing-library/react

Biblioteca responsável por renderizar componentes React durante os testes.

Ela permite validar o comportamento dos componentes da mesma forma que o usuário interage com a aplicação.

---

## @testing-library/dom

Disponibiliza funções utilitárias para localizar elementos na árvore HTML durante os testes.

Essa biblioteca é utilizada internamente pelo React Testing Library.

---

## @testing-library/jest-dom

Adiciona novos _matchers_ para facilitar as validações durante os testes.

Entre eles:

- verificar se um elemento existe;
- verificar se um elemento está visível;
- verificar atributos;
- verificar estados;
- verificar conteúdo textual.

---

## @testing-library/user-event

Permite simular ações realizadas pelo usuário.

Entre elas:

- clique;
- digitação;
- seleção;
- scroll;
- navegação por teclado.

Essas interações tornam os testes mais próximos do comportamento real da aplicação.

# Criando o arquivo vitest.config.ts

Na raiz do projeto, criar o arquivo:

```text
vitest.config.ts
```

Conteúdo:

```typescript
import { defineConfig } from 'vitest/config';
import react from '@vitejs/plugin-react';

export default defineConfig({
  plugins: [react()],

  resolve: {
    tsconfigPaths: true,
  },

  test: {
    globals: true,

    environment: 'jsdom',

    setupFiles: ['./src/test/setup.ts'],

    css: true,

    coverage: {
      provider: 'v8',
      reporter: ['text', 'html'],
    },
  },
});
```

---

# Explicação da configuração

## plugins

Mantém o mesmo plugin React utilizado pela aplicação.

Isso garante que os componentes React sejam interpretados corretamente durante a execução dos testes.

---

## resolve.tsconfigPaths

```typescript
resolve: {
  tsconfigPaths: true,
}
```

Como este Template utiliza o Vite 8, a resolução de Path Aliases é realizada nativamente pelo próprio Vite.

Dessa forma, não é mais necessário utilizar o pacote `vite-tsconfig-paths`.

Essa configuração permite utilizar normalmente os aliases definidos no TypeScript durante a execução dos testes.

---

## globals

```typescript
globals: true;
```

Permite utilizar funções como:

- describe;
- it;
- test;
- expect;
- beforeEach;
- afterEach.

Sem necessidade de importação manual em todos os arquivos de teste.

---

## jsdom

Simula um navegador dentro do ambiente Node.js.

Como os testes são executados fora de um navegador real, essa biblioteca fornece uma implementação do DOM necessária para renderizar componentes React durante os testes.

---

---

## environment

```typescript
environment: 'jsdom';
```

Define que todos os testes serão executados utilizando um ambiente que simula um navegador.

Como os testes são executados no Node.js e não em um navegador real, essa configuração é indispensável para aplicações React.

O `jsdom` fornece uma implementação do DOM, permitindo que componentes React sejam renderizados normalmente durante os testes.

Sem essa configuração, testes envolvendo componentes React apresentariam erros relacionados à inexistência dos objetos do navegador, como `window`, `document` e outros elementos da API Web.

---

## setupFiles

```typescript
setupFiles: ['./src/test/setup.ts'];
```

Define qual arquivo deverá ser carregado automaticamente antes da execução de qualquer teste.

Esse arquivo centraliza configurações compartilhadas entre todos os testes do projeto.

No momento, sua responsabilidade é registrar os _matchers_ fornecidos pelo Testing Library.

No futuro, outras configurações globais poderão ser adicionadas sem necessidade de alterar individualmente cada arquivo de teste.

---

## css

```typescript
css: true;
```

Permite que arquivos CSS sejam importados normalmente durante a execução dos testes.

Essa configuração evita erros quando componentes React importam arquivos de estilo.

Embora neste momento o projeto ainda não possua testes envolvendo componentes estilizados, essa configuração deixa a infraestrutura preparada para futuras implementações.

---

## coverage

```typescript
coverage: {
  provider: 'v8',
  reporter: ['text', 'html'],
}
```

Configura a geração do relatório de cobertura dos testes.

Foram definidos dois formatos de saída.

### text

Exibe um resumo diretamente no terminal ao final da execução.

Esse formato facilita uma rápida visualização da cobertura durante o desenvolvimento.

---

### html

Gera um relatório navegável em HTML.

Esse relatório poderá ser aberto posteriormente em qualquer navegador, permitindo uma análise detalhada da cobertura do projeto.

---

# Validação da configuração

Após concluir toda a configuração da infraestrutura, executar o comando abaixo.

```bash
pnpm test:run
```

Durante a execução, o Vitest deverá localizar automaticamente o arquivo:

```text
src/test/setup.test.ts
```

Em seguida, o teste será executado para validar toda a infraestrutura de testes.

Um resultado semelhante ao exemplo abaixo deverá ser apresentado.

```text
RUN  v4.x.x

✓ src/test/setup.test.ts (1 test)
  ✓ Infrastructure
    ✓ should configure the testing environment correctly

Test Files  1 passed (1)
Tests       1 passed (1)

Duration ...
```

No seu ambiente, o resultado esperado deverá ser semelhante ao exemplo abaixo.

```text
RUN  v4.1.10

✓ src/test/setup.test.ts (1 test) 5ms
  ✓ Infrastructure (1)
    ✓ should configure the testing environment correctly 2ms

Test Files  1 passed (1)
Tests       1 passed (1)

Start at 21:24:54
Duration 5.47s
```

Os tempos de execução poderão variar de acordo com o computador utilizado.

O importante é que o teste seja executado com sucesso e que o Vitest finalize informando que todos os testes foram aprovados.

Esse resultado confirma que:

- o Vitest foi instalado corretamente;
- o ambiente `jsdom` foi inicializado corretamente;
- o arquivo `setup.ts` foi carregado;

# Etapa 3 — Configuração da Integração Contínua (CI/CD)

---

# Objetivo

Nesta etapa será configurada a infraestrutura de Integração Contínua (Continuous Integration - CI) do projeto.

O objetivo é garantir que todas as alterações enviadas para o repositório sejam automaticamente validadas antes de serem incorporadas ao código principal.

Essa validação automática reduz a possibilidade de erros, mantém a qualidade do código e garante que o Template permaneça sempre estável.

Ao final desta etapa, o projeto estará preparado para executar automaticamente as principais verificações sempre que ocorrer um Push ou um Pull Request.

---

# O que é CI/CD?

CI significa **Continuous Integration (Integração Contínua)**.

Consiste na execução automática de tarefas de validação sempre que alterações forem enviadas para o repositório.

Entre essas validações normalmente estão:

- Instalação das dependências;
- Verificação de qualidade do código;
- Execução do Lint;
- Execução dos testes;
- Execução do Build.

Caso alguma dessas etapas falhe, a alteração poderá ser corrigida antes de ser integrada ao projeto.

- Configuração da instalação automática das dependências;
- Execução automática do Lint;
- Execução automática dos testes;
- Execução automática do Build;
- Validação da Pipeline.

---

# Por que utilizar GitHub Actions?

Como este Template será armazenado em um repositório GitHub, o GitHub Actions oferece integração nativa com o projeto.

Isso elimina a necessidade de instalar ferramentas externas apenas para realizar validações automáticas.

Além disso, qualquer projeto criado a partir deste Template já herdará automaticamente essa configuração.

# Criando o Workflow

Criar o arquivo:

```text

```

Este arquivo será responsável por definir toda a Pipeline de Integração Contínua.

---

# Conteúdo do arquivo

```yaml
name: Continuous Integration

on:
  push:
    branches:
      - main
      - develop

  pull_request:
    branches:
      - main
      - develop

jobs:
  validation:
    runs-on: ubuntu-latest

    steps:
      - name: Checkout do repositório
        uses: actions/checkout@v4

      - name: Instalar PNPM
        uses: pnpm/action-setup@v4
        with:
          version: 10

      - name: Configurar Node.js
        uses: actions/setup-node@v4
        with:
          node-version: 24
          cache: pnpm

      - name: Instalar dependências
        run: pnpm install

      - name: Executar ESLint
        run: pnpm lint

      - name: Executar Testes
        run: pnpm test:run

      - name: Executar Build
        run: pnpm build
```
